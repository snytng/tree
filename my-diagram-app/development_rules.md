# 開発ガイドライン

このドキュメントは、My Diagram App プロジェクトにおける開発の進め方、品質維持、およびチーム連携のためのルールを定めます。

## 1. ドキュメント管理とトレーサビリティ

### 1.1 ドキュメントファースト原則
- **目的**: 実装前に要件と設計を明確にし、手戻りを最小限に抑える。
- **[背景]**: コードを書き始めてから仕様の矛盾に気づくと修正コストが跳ね上がるため。また、AIとの認識の齟齬を早い段階で解消するため。
- **ルール**: 機能を実装・修正する際は、必ず以下の順序でドキュメントを更新し、フェーズを進めること。
    1.  `backlog.md`: タスクを起票し、優先順位を決定する。
    2.  `spec.md`: 外部から見た挙動（仕様）とテスト基準を定義する。
    3.  `design.md`: 内部構造やアルゴリズム、データ構造を設計する。
    - **UIロジックの同期**: `design.md` で定義されたリスト順序（[D-039]）や状態遷移（[D-042]）は、`App.jsx` の `toolbarConfig` 等の実装に一対一で反映させること。

### 1.2 トレーサビリティの確保
- **目的**: 要件から設計、実装、テストへの繋がりを明確にし、変更の影響範囲を把握しやすくする。
- **[背景]**: どのコードがどの機能（要求）のために存在するのかを明示することで、デバッグやリファクタリング時に「消していいコードか」を即座に判断可能にするため。
- **ルール**: 新機能や変更点には一意のID（例: `[S-xxx]`, `[D-xxx]`）を付与し、`mapping.json` でそれらの関係性を管理すること。
- **`mapping.json` のスキーマ**: 4つのセクションで構成する。

| セクション | 内容 | 記録タイミング |
| :--- | :--- | :--- |
| `traceability` | S→D の縦方向の実現関係 (`realizes`) | spec.md / design.md 更新時 |
| `dependencies` | D→D の横方向の依存・影響関係 (`impacts`, `depends-on`) | design.md 更新時・影響分析時 |
| `implementations` | D→ファイルパスの実装対応 | 実装完了時 |
| `sharedResources` | 共有リソース（Yjsマップ、localStorage等）と使用元D-ID・ファイル一覧 | 新リソース追加時・設計変更時 |

- **関係タイプの定義**:
    - `realizes`: 仕様が設計によって実現される（S→D）。
    - `impacts`: 変更元の設計を修正すると、変更先の設計の前提が壊れる（D→D）。`reason` フィールドに影響の具体的内容を記述。
    - `depends-on`: 変更先の設計の正常動作が、変更元の設計の存在に依存する（D→D）。

### 1.3 抽象化と再現性の維持
- **目的**: 特定のライブラリに依存しない論理構造を記述し、将来の技術スタック変更やコード再生成を容易にする。
- **ルール**:
    - **アルゴリズムの言語化**: 自動レイアウトやデータ変換などのロジックは、ライブラリのAPI名だけでなく、ステップバイステップの論理手順（疑似コードに近い形式）で記述する。
    - **データモデルの定義**: 内部状態（Nodes/Edges等）が持つべき「意味的な情報」を定義し、ライブラリ固有のプロパティ（例: `reactflow.position`）とは区別して管理する。
    - **ライブラリ依存の分離**: 設計書内で「何をするか（論理）」と「どのライブラリで実現するか（実装）」を明確に分けて記述する。

### 1.4 ドキュメント更新フロー
- **目的**: すべてのドキュメントが一貫して最新状態を保つようにし、更新漏れを防止する。
- **[背景]**: 仕様・設計は更新したが README や USAGE が古いまま、またはその逆のケースを防ぐため。
- **更新タイミングと対象ドキュメント**:

| タイミング | 更新対象 | 内容 |
| :--- | :--- | :--- |
| タスク起票時 | `backlog.md` | 新規項目を追加し、ステータスを `[ ] Todo` に設定。 |
| 設計フェーズ | `spec.md`, `design.md`, `mapping.json` | 仕様 (`[S-xxx]`) と設計 (`[D-xxx]`) を追記し、マッピングを追加。 |
| 実装完了時 | `backlog.md`, `development_log.md` | ステータスを `[x] Done` に変更。開発ログに日時付きで記録。 |
| 機能追加・大きな変更の区切り | `README.md`, `USAGE.md` | 新機能の概要・操作方法を反映。 |
| セッション終了時 | `development_log.md` | 現在の状況と「次に何をすべきか」を記録。 |

- **README.md の更新ルール**: 新しいビュータイプの追加、操作体系の変更、技術スタックの変更など、プロジェクトの外観や使い方に影響する変更があった場合に更新する。リポジトリルート (`README.md`) に配置。
- **USAGE.md の更新ルール**: 操作手順やキーボードショートカットの追加・変更があった場合に更新する。`my-diagram-app/USAGE.md` に配置。
- **チェックリスト**: 以下の問いにすべて「はい」と答えられることを確認してから区切りとする。
    1. `backlog.md` のステータスは最新か？
    2. `spec.md` / `design.md` / `mapping.json` は実装と一致しているか？
    3. `README.md` / `USAGE.md` に新機能や操作変更が反映されているか？
    4. `development_log.md` に日時付きで記録したか？

## 2. コード実装と品質

### 2.1 設計への忠実性
- **目的**: ドキュメントで合意された設計に基づき、一貫性のあるコードベースを維持する。
- **[背景]**: AIが勝手に「良かれと思って」設計外のコードを書くと、全体の整合性が崩れ、後の自動レイアウトなどの計算に悪影響を及ぼすため。
- **ルール**: 確定した設計 (`design.md`) に基づき実装を行うこと。設計と異なる実装が必要になった場合は、`design.md` を更新し、関係者と合意を得ること。

### 2.2 Yjs同期ロジックの原則
- **目的**: 共同編集機能の安定性とパフォーマンスを確保する。
- **ルール**:
    - Yjsのトランザクションには `origin: 'local'` を付与し、自己発生イベントによる無限ループやカクつきを防止する。
    - Yjsからデータを取得する際は、React側の `selected` 状態など、ローカルでのみ保持すべき状態が上書きされないよう、既存のReact状態とマージして同期を行う。

### 2.3 インタラクション制御の原則
- **目的**: カスタムUI（入力フォーム等）とライブラリ標準機能の競合を防ぐ。
- **[背景]**: ノード名の入力中に矢印キーを押してノードが移動してしまうような、ユーザーの予期しない挙動（UXの低下）を防止するため。
- **ルール**:
    - ノード内の入力要素（input/textarea等）での操作が、キャンバス全体のキーボードナビゲーションやノード移動を誘発しないよう、必ず `e.stopPropagation()` を呼び出すこと。
    - ダブルクリック編集などのカスタム操作を導入する場合、ライブラリ側の既定動作（ズーム等）と競合しないか確認し、必要に応じて既定動作を無効化（例: `zoomOnDoubleClick={false}`）すること。

### 2.4 構造的繋ぎ替え（スプライス）の原則
- **目的**: 既存の接続を維持しつつ、新しい要素を間に挿入する際のデータ整合性を保証する。
- **ルール**:
    - **原子性の確保**: 「新しいエッジの追加」と「古いエッジの削除」は、必ず同一の Yjs トランザクション内で実行すること。
    - **多重接続の考慮**: 単一の親だけでなく、複数の入力を受けているノードに対しても、全てのパスが新ノードを経由するようにループ処理で一括処理すること。
    - **論理座標の優先**: スプライス直後の座標は、基準ノードからの相対オフセット（例: `x - 360`）を与え、自動レイアウト側での配置順序のヒントとすること。

### 2.5 横断的影響分析 (Cross-Component Impact Analysis)
- **目的**: ある機能の変更が、同じデータを参照する他のコンポーネントやサーバーに波及する影響を漏れなく検出する。
- **[背景]**: B-033（マルチプロジェクト）でフロントエンドのYjsルーム名が `mda_{projectId}` に変更されたにもかかわらず、MCPサーバー側は旧ルーム名 `react-flow-demo-room` のまま取り残された。影響分析の手順が定義されていなかったため、ドキュメント整備完了後にユーザーの指摘で初めて発覚した（2026-05-30）。
- **ルール**:
    - **影響分析の義務**: 以下のカテゴリに該当する変更を行う場合、実装前に「影響を受ける既存コンポーネント一覧」を洗い出し、`design.md` または `backlog.md` に明記すること。
        1. **データモデルの変更**: Yjsマップ名、ルーム名、localStorageキー名の変更・追加。
        2. **通信プロトコルの変更**: WebSocket/WebRTC/SSE のエンドポイントやメッセージ形式の変更。
        3. **外部I/Fの前提変更**: インポート/エクスポート形式、MCPツールの入出力スキーマに影響する変更。
    - **`mapping.json` を使った影響分析手順**:
        1. 変更対象の設計ID `[D-xxx]` を特定する。
        2. `mapping.json` の `sharedResources` で、その D-ID が使用している共有リソースを列挙する。
        3. 同じリソースの `usedBy` に含まれる**他の D-ID** が影響先候補。`files` で実装ファイルも特定する。
        4. `dependencies` の `impacts` / `depends-on` で、既知の横方向依存を確認する。
        5. 影響先候補に対し、変更が前提を壊すか判定する。壊す場合は `dependencies` に `impacts` エントリを追記し、連動バックログを起票する。
    - **影響先チェックリスト**: 上記手順に加え、最低限以下のコンポーネントへの影響を確認すること。
        - [ ] フロントエンド (`App.jsx`, 各ビューコンポーネント)
        - [ ] MCPサーバー (`mcp-server/index.js`)
        - [ ] 永続化 (IndexedDB, localStorage)
        - [ ] 通信 (y-websocket, y-webrtc)
    - **連動バックログの起票**: 影響があると判明した場合、修正タスクをバックログに即座に起票し、元タスクとの依存関係を明記すること。
    - **`mapping.json` の更新義務**: 設計変更時、影響分析の結果として以下を必ず更新すること。
        1. `dependencies`: 新たに判明した `impacts` / `depends-on` 関係を追加。
        2. `implementations`: 実装完了後、D-ID に対応するファイルパスを追加・更新。
        3. `sharedResources`: 新しい共有リソース（Yjsマップ、localStorageキー等）を追加した場合、`usedBy` と `files` を記録。

## 4. 開発プロセス (備忘録)
- **ドキュメントファースト**: 機能を実装・修正する前に、必ず `spec.md` (要求) および `design.md` (設計) を更新し、変更方針を確定させる。
- **トレーサビリティ**: 新機能や変更点には一意のID（[S-xxx], [D-xxx]）を付与し、`mapping.json` でそれらの関係性を管理する。
- **影響分析**: 設計変更時は `mapping.json` の `sharedResources` → `dependencies` を辿り、影響先を特定する。
- **コードへの反映**: 確定した設計に基づき実装を行う。実装完了後、`mapping.json` の `implementations` を更新する。

## 5. UI/UX デザイン原則
- **要素の干渉防止**: 操作パネル（Panel）は、画面サイズに関わらず重ならないよう配置を考慮する。ボタンが多い場合は垂直にスタックさせる。

## 6. トラブルシューティング
- **デバッグログの活用**: インポート/エクスポートなどの複雑なデータ処理には `console.group` を使用した詳細なログを出力し、ユーザーが問題を報告しやすくすること。
- **レイアウト報告時のルール**: 配置の不具合を報告する際は、必ず「デバッグ情報」ボタンで取得した JSON を添付し、期待する結果と比較できるようにすること。

## 7. バックログ管理 (backlog.md)

### 7.1 ファイルの役割
- **目的**: 将来実装したい機能やアイデアをストックし、開発の優先順位を管理する。
- **運用**: 
    - **ステータス管理**: `[ ] Todo`, `[/] Doing` (実装中), `[T] Testing` (実装完了・ユーザー検証待ち), `[x] Done`
    - **履歴の保持**: 完了したタスク (`[x] Done`) はリストから削除せず、完了のマークを付けて末尾または Done セクションに残し続けること。プロジェクトの進化の軌跡として管理する。
    - **進行中のタスク（[/] または [T]）は、優先度に従い `backlog.md` のリストの先頭へ物理的に移動させること。**
    - **[背景]**: 長大なバックログの中でAIが現在のタスクを見失うのを防ぎ、コンテキスト読み込み直後に「今何に注力すべきか」を確実に把握させるため。
    - 実装フェーズに移行する際は、詳細な要件を `spec.md` へ、設計を `design.md` へ昇格させて転記すること。

### 4.2 プロジェクト管理の原則
- **プロジェクトの同一性**: ZIPインポート時は既存データをクリアし、新しいプロジェクトを開始する。
- **メタデータの同期**: プロジェクト名は `projectMeta` を通じて全ユーザー間で共有・表示すること。

## 8. 実装の制御

### 8.1 実装開始のトリガー
- **ルール**: AI（Gemini）は、ユーザーから**「実装開始」**という明確な指示があるまで、コードの生成や既存ファイルの破壊的な修正を自発的に行わないこと。
- **[背景]**: 思考を整理している最中にAIがコードを生成し始めると、議論が中断されたり、中途半端なコードが混入したりするリスクを避けるため。
- **バックログの自動進行禁止**: 一つのタスクが完了（Done）した際、Gemini は自発的に次のバックログ項目を選択して開発（要求定義や設計）を開始してはならない。必ずユーザーからの次の指示を待つこと。
- **目的**: ユーザーの作業ペースを尊重し、設計の吟味に十分な時間を確保するため。

## 9. アジャイル開発サイクル

### 9.1 サイクル・ステップ
1. **要求・テスト定義 (Todo -> Doing)**: 実装前に、Gemini が `spec.md` に詳細な挙動と「どのようなテストをパスすれば完了か（テスト仕様）」を提示する。
2. **ユーザー確認 (Doing -> Ready)**: ユーザーが提示されたテスト仕様をレビューし、合意する。この時点でステータスを `Ready` に更新する。
3. **実装開始 (Ready -> Doing)**: ユーザーの「実装開始」の指示を受け、Gemini がコードを実装する。
4. **検証と受入 (Doing -> Done)**: ユーザーが実装物をテストし、ステップ1で決めた基準を満たせば `Done` とし、ドキュメントとログを更新する。

### 9.2 Definition of Ready (準備完了の定義)
- 実装内容が `spec.md` および `design.md` に反映されている。
- **「これができたらOK」という検証手順が明記されている。**
- ユーザーから実装着手の合意が得られている。

## 10. セッションの中断と復帰

### 10.1 開発ログの運用
- **日付の記録**: `development_log.md` に記録する際は、必ず現在の日付と時刻（日本時間）を `YYYY-MM-DD HH:mm` 形式で正確に記載すること。**前のエントリの日付をそのままコピーしない。**
- **履歴の保持**: 開発ログは「追記型」であり、過去のエントリを削除または上書きしてはならない。
- **目的**: 開発の時系列を正しく把握し、PC再起動後などの復帰時に「いつ、どの変更が行われたか」をAIとユーザーが正確に認識できるようにするため。
- **中断時の記録**: PCの再起動や作業中断が予想される場合、`development_log.md` の末尾に現在の状況と「次に何をすべきか」を明記する。
- **復帰時の確認**: AIはセッション開始時に必ず `backlog.md` のステータスと `development_log.md` の最終行を確認し、現在のフェーズ（実装中なのか、検証待ちなのか）を特定してから発言すること。
- **[背景]**: 会話の中断（セッション切れ）が起きても、AIが自律的に状況をキャッチアップし、ユーザーに「何をしていましたっけ？」と聞き返さずに済むようにするため。

## 11. 停滞時の「調査フェーズ」強制移行ルール

### 11.1 試行回数の制限と判断
- **ルール**: 同一箇所の不具合修正や機能実装が **2回連続で失敗** した場合、AIは自ら実装フェーズの継続を断念し、「調査フェーズ」への移行を宣言すること。
- **[背景]**: 修正が繰り返される原因は、根本的な前提（データ構造、CSSの優先順位、Propsの受け渡し等）の誤認にあるため。無理な提案によるハルシネーションを防ぐ。

### 11.2 調査フェーズの進め方
- **最小単位の変更**: 一度に複数のファイルを修正せず、1箇所（例：CSSの1行だけ、Propsの名称1つだけ）を変更し、その「反応」をユーザーに確認してもらうこと。
- **推測の排除**: 「〜だと思います」という推測でコードを書く前に、現在の状態をコンソールログやデバッグ出力で確認する提案を行うこと。

## 12. 開発態度のクレド (Our Development Credo)

セッションの開始時、または新しいタスクへの着手時、AIとユーザーは以下の信条を確認し、合意の上で「よし！」と号唱して開始する。

1.  **Truth over Speed**: 速さよりも、正しさと確実さを優先する。
2.  **Small Steps**: 大きな修正ではなく、検証可能な最小の変更を積み重ねる。
3.  **Honest Doubt**: 分からないこと、確証が持てないことは、正直に「分からない」と伝え、調査に戻る。
4.  **Stay Disciplined**: 常にルールとドキュメントを羅針盤とし、場当たり的な修正を行わない。
